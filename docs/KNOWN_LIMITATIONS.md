# FlakyGuard AI: Known Limitations & Threat Analysis

This document provides a comprehensive, transparent record of the scientific, methodological, and practical limitations of FlakyGuard AI. Prospective users, researchers, and academic reviewers should evaluate all findings within these boundaries.

---

## 1. Observational Natural Language Issues vs. Dynamic Execution Traces

- **The Limitation**: FlakyGuard AI operates on post-hoc developer-written natural language issue reports and pull request descriptions extracted from GitHub.
- **The Implication**:
  - The model observes developer symptoms, error snippets, and debugging vocabulary *after* an engineer has noticed an anomaly and written an issue.
  - The model does **not** directly inspect runtime execution logs, non-deterministic JVM thread schedules, operating system context switches, or memory allocations.
  - An issue report that omits technical keywords (e.g. simply reporting "Test failed again") cannot be diagnosed effectively by lexical models.
- **Appropriate Scope**: FlakyGuard AI is designed as a **developer triage assistance tool** for issue trackers and CI failure bug reporters, **not** an in-process dynamic testing monitor.

---

## 2. Lexical TF-IDF Feature Representation Limits

- **The Limitation**: The feature representation relies on unigram and bigram Term Frequency-Inverse Document Frequency (TF-IDF) with sublinear scaling.
- **The Implication**:
  - Word order beyond adjacent bigrams is discarded (Bag-of-Words assumption).
  - Deep semantic relationships, long-range variable references, syntactic structure in embedded code blocks, and stack trace hierarchies are not explicitly modeled.
  - Code snippets embedded in markdown (e.g. `assert timeout == 5000`) are tokenized as disjoint lexical terms rather than parsed Abstract Syntax Trees (ASTs).

---

## 3. Severe Root-Cause Class Sparsity & Imbalance

- **The Limitation**: The root-cause taxonomy contains 589 verified flaky issues distributed across 13 distinct classes.
- **The Implication**:
  - The distribution is heavily skewed toward dominant timing and concurrency classes:
    - `Async Wait`: 105 samples (17.8%)
    - `Concurrency`: 94 samples (16.0%)
    - `Network`: 86 samples (14.6%)
  - Conversely, rare categories suffer from severe sample sparsity:
    - `Too Restrictive Range`: 6 samples (1.0%)
    - `Test Suite Timeout`: 5 samples (0.85%)
  - In a standard 80/20 test split ($N=118$), a rare class may contain only 1 sample in the test set. A single misclassification drops that class's recall to 0.0, causing severe volatility in Macro-F1.
  - While grouping into 4 macro categories mitigates this sparsity, it sacrifices fine-grained diagnostic specificity.

---

## 4. Post-Hoc Explainability vs. Causal Faithfulness

- **The Limitation**: Feature attributions generated by linear model coefficients, SHAP, and LIME reflect **statistical associations in the text training distribution**, not causal mechanisms of hardware failure.
- **The Implication**:
  - A token with a high positive weight (e.g., `flaky`, `timeout`, `race`) indicates that the presence of this word in an issue report strongly correlates with author-labeled flakiness.
  - It does **not** prove that a race condition was the physical or algorithmic cause of the test failure.
  - Feature importances from Random Forest (Mean Decrease in Impurity / Gini importance) are strictly non-negative ($\ge 0$) and do not indicate directional polarity.
  - As demonstrated in our audit, distribution shift across repository clusters can invert the sign of language-specific tokens (e.g. `goroutine` inverted from $-0.1708$ to $+0.0387$).

---

## 5. Cross-Language Confounding Factors

- **The Limitation**: In the Leave-One-Language-Out (LOLO) experiment, each held-out partition represents a distinct programming language ecosystem (C, Go, Java, JavaScript, Python).
- **The Implication**:
  - Language boundaries strongly correlate with repository domain, community size, testing frameworks (`pytest`, `JUnit`, `mocha`, `go test`), and issue reporting conventions.
  - Therefore, performance drop-offs (such as Java's lower transfer Macro-F1 of 0.5144) cannot be causally attributed to the Java programming language syntax or JVM architecture alone. They are confounded by community writing styles, repository maturity, and test framework vocabularies.

---

## 6. Repeated Partitions vs. Independent Folds

- **The Limitation**: The repository-independent generalization experiment uses `GroupShuffleSplit` across 10 random seeds.
- **The Implication**:
  - Within any single partition, repository overlap between train and test is strictly zero ($\text{Train} \cap \text{Test} = \emptyset$).
  - However, across different seeds, repositories are repeatedly resampled. The 10 evaluations are **repeated random partitions**, not mutually exclusive cross-validation folds.
  - The reported standard deviation ($\pm 0.0239$ for LR, $\pm 0.0267$ for RF) captures variance across random repository groupings, but partition metrics are not completely statistically independent.
